# XetSharp — Implementation Plan

Goal: a modern, high-performance, idiomatic C# client for the [Xet protocol](https://huggingface.co/docs/xet/main/en/index) (spec v1.1.0), able to download and upload files on the Hugging Face Hub interoperably with the Rust reference implementation ([xet-core](https://github.com/huggingface/xet-core)).

## Guiding principles

- **Verification first.** The spec's core promise is determinism: independent implementations MUST produce identical hashes, objects and API behaviour. Every layer gets a verification suite before (or alongside) its implementation, cross-checked against xet-core.
- **Bottom-up layering.** Each layer is pure and independently testable; network I/O only enters at the CAS client layer.
- **Idiomatic, modern .NET.** `net10.0`, nullable enabled, `Span<T>`/`IBufferWriter<byte>`-based parsing, `System.IO.Pipelines` where it pays, AOT-compatible, no reflection-based serialization in hot paths.
- **TUnit** for all tests; property-based tests where the spec defines invariants (e.g. chunk boundaries), golden-file tests where it defines exact bytes.

Detailed protocol digests (constants, binary layouts, endpoint schemas, gotchas) distilled from the spec live in [docs/protocol-notes/](docs/protocol-notes/).

## Protocol layers (bottom-up)

1. **Primitives** — `MerkleHash` (256-bit hash; canonical hex form byte-reverses each 8-byte group). ✅ walking skeleton
2. **Chunking** — gearhash-based content-defined chunking with the spec's table, mask, and min/target/max sizes. ✅ walking skeleton
3. **Hashing** — chunk hashes, xorb hashes (content-defined Merkle aggregation), file hashes (salted finalization), verification-range hashes, HMAC-keyed chunk hashes for dedup shards. ✅ walking skeleton
4. **Xorb format** — serialize/deserialize chunks with per-chunk headers and compression (none / LZ4 / byte-grouped LZ4). ✅
5. **Shard format** — binary shard reader/writer: header, file-info section, CAS-info section, footer, HMAC key handling. ✅
6. **CAS API client** — typed `HttpClient`-based client: token acquisition/refresh from the Hub, reconstruction endpoint, global-dedupe chunk query, xorb upload, shard upload; retry/backoff and error semantics per spec. ✅ read path (reconstruction v2 + v1 fallback, token cache, retry handler); upload endpoints pending M3
7. **Download pipeline** — file ID → reconstruction → parallel ranged fetches of xorb data → decompress → reassemble → verify file hash. Term-range caching. ✅
8. **Upload pipeline** — chunk → dedupe (local + global) → pack xorbs → build shard → upload xorbs then shard → commit via Hub. 
9. **Public API** — a small, discoverable surface (e.g. `XetClient.DownloadAsync(repo, path, destination)`, `UploadAsync`), `Microsoft.Extensions.*`-friendly (DI, `ILogger`, `IHttpClientFactory`) but not requiring it. ✅ download half (`XetClient`, `XetClientOptions`, injectable `HttpClient`); `ILogger` and a DI extension deferred until upload lands

## Verification suite strategy

Three rings, in order of feedback speed:

1. **Golden vectors (offline, fast).** xet-core's own test suite publishes cross-implementation vectors: 130 chunk-boundary cases (SplitMix64-seeded and edge-case pattern data) and 18 Merkle xorb/file-hash cases — all ported verbatim into the TUnit suite. Chunk-hash and range-hash vectors are generated by a checked-in blake3-only harness (`tools/vectors/`). CI needs no Rust toolchain. The format layer adds golden files from the `xet-team/xet-spec-reference-files` dataset: all four shard variants, the 796-chunk listing, and a 10-chunk prefix of the real xorb (`tests/XetSharp.Tests/ReferenceFiles/`). The two artefacts too big to vendor — the 63 MB CSV and the whole 14 MB xorb — drive tests that opt in via `XETSHARP_REFERENCE_DIR`. The API layer adds sanitized *captured responses* (`tests/XetSharp.Tests/CapturedResponses/`): real reconstruction bodies for both API versions, including the multi-xorb and mid-chunk-range cases, so parsing is pinned to what the service actually sends.
2. **Property tests (offline).** Invariants from the spec: chunk sizes always within [min, max]; chunking is deterministic and content-defined (inserting data only shifts boundaries locally); round-trip xorb/shard serialize→parse; compression round-trips.
3. **Live interop (online, opt-in).** Download a known file from a public Hub repo and byte-compare with the `resolve/` HTTP download; later, upload to a scratch repo and re-download via hf_xet. Gated behind `XETSHARP_LIVE_TESTS=1` so CI and local runs stay hermetic by default. The download half is in place: `LiveDownloadTests` resolves, range-downloads (including a range straddling two xorbs) and byte-compares against the plain HTTP route, then downloads the whole 63 MB reference file and checks it against both its published file ID and its SHA-256. No credentials needed — the Hub issues anonymous read tokens for public repos.

## Milestones

- **M0 — Walking skeleton** ✅: solution + TUnit harness; `MerkleHash`; gearhash chunker; chunk/xorb/file/verification hashing; 162 tests proving bit-identical output vs xet-core reference vectors.
- **M2 — Formats** ✅ *(taken before M1: the download pipeline has to parse xorb chunk records anyway, so the pure format layer is the cheaper thing to nail down first)*: xorb serializer/reader with all three compression schemes; MDB shard reader/writer round-tripping all four published reference shards byte for byte; HMAC chunk matching for dedupe responses. 212 tests.
- **M1 — Download** ✅: file-ID resolution off the resolve endpoint's redirect; a token cache that refreshes 30 s early and re-mints on a CAS `401`; `/v2/reconstructions` with `/v1` fallback; signed multi-range xorb fetches with a `multipart/byteranges` reader; ordered term assembly that decompresses chunk by chunk (so a term costs its *compressed* size in memory, not what it expands to) with bounded look-ahead prefetching; per-term `unpacked_length` checks plus whole-file hash and SHA-256 verification. 301 tests, four of them live against the Hub — the 63 MB reference file downloads and re-hashes to the file ID xet-core published for it.
- **M3 — Upload**: dedupe, xorb packing, shard build, upload flow against a scratch repo.
- **M4 — Performance & polish**: benchmarks (BenchmarkDotNet) vs hf_xet, SIMD-friendly gearhash inner loop, parallelism tuning, NuGet packaging, docs.

## Decisions taken (flag if you disagree)

- **BLAKE3** via the `Blake3` NuGet package (xoofx — native SIMD bindings, the fastest managed option). A pure-managed fallback could come later if the native dependency is a problem.
- **`net10.0` only** to start; multi-targeting (e.g. `netstandard2.0` for older consumers) deferred until the API stabilises.
- **CPM + slnx**, warnings as errors, AOT-compatible library.
- Test vectors are **vendored** (generated from xet-core by a checked-in harness) rather than generated at test time, keeping CI free of a Rust toolchain.
- **LZ4** via `K4os.Compression.LZ4.Streams` — the only maintained managed LZ4 for .NET, and the *frame* API is the one that matters (see below). Pure managed, so AOT stays fine.
- **No new dependencies for the HTTP layer**: `System.Text.Json` source generation (so no reflection, AOT intact), a plain `DelegatingHandler` for retry rather than Polly, and a hand-written `multipart/byteranges` reader. `IHttpClientFactory` users pass their own `HttpClient` through `XetClientOptions`; nothing requires `Microsoft.Extensions.*`.
- **`HEAD`, not `GET`, on the resolve endpoint.** The spec says `GET`, but with redirects disabled a file that is *not* on Xet answers with its whole body. `HEAD` returns the same Xet headers and never downloads anything by accident.
- **Whole-file downloads verify twice**: the chunks are re-aggregated into a file hash and compared to the file ID, and the written bytes are checked against the Hub's `X-Linked-Etag` SHA-256. Both are on by default and can be turned off in `XetDownloadOptions`. Partial downloads verify per-term `unpacked_length` only — the other two are not computable from a slice.

## Corrections the reference bytes forced

The spec's prose was wrong or silent in four places, each caught by round-tripping real reference
artefacts rather than by reading. All four are written up in [docs/protocol-notes/xorb-and-shard-formats.md](docs/protocol-notes/xorb-and-shard-formats.md):

- Compression scheme `1` is the LZ4 **frame** format, not a bare LZ4 block.
- The reference xorb carries four trailing bytes (`XETB`) that no version of the spec mentions.
- A shard's `chunk_byte_range_start` holds uncompressed-stream offsets, not offsets into the serialized xorb.
- Both of the shard footer's "reserved" regions hold real fields, so zeroing them breaks round-tripping — and the SHA-256 in the file-metadata record is byte-swapped like every other hash.

## What live traffic corrected in turn

Building M1 against the real service turned up four more gaps between the spec pages and what the
Hub sends today. All are written up in [docs/protocol-notes/cas-api-and-flows.md §8](docs/protocol-notes/cas-api-and-flows.md#8-what-live-traffic-adds):

- The resolve response points at auth with a `Link: …; rel="xet-auth"` header. The `X-Xet-Cas-Url` / `X-Xet-Access-Token` headers an earlier note guessed at do not exist — but `X-Linked-Etag` does, and it is the file's SHA-256.
- The signed byte range is not the `X-Xet-Signed-Range` query parameter the spec's examples show; it lives inside the CloudFront `Policy` as a `ByteRange.ExpectedHeader` condition. Same rule — the `Range` header must match exactly — but a client cannot read it off the URL, and a `GET` with no `Range` is a 403 rather than a full download.
- The v1 `fetch_info` entry shape (`range` + `url` + `url_range`), which the spec names but never defines.
- Anonymous access is real: no Hub token at all yields a working read token for a public repository.

## Open questions for you

- Package identity: publish as `XetSharp` on NuGet when ready?
- Any interest in a `netstandard2.0`/`net8.0` multi-target early (e.g. for use inside other tools), or is `net10.0`-only fine for now?
- The shard footer fields above are undocumented; I've surfaced the byte-count totals on `ShardFooter` so shards round-trip, and reject shards carrying lookup tables (which this library never writes). Happy to make that lenient instead if you'd rather parse everything xet-core can emit.
- Concurrency is currently fixed (`MaxConcurrentDownloads = 8`, a 128 MiB prefetch budget). xet-core scales it adaptively with observed bandwidth; worth doing in M4, or sooner if you want it.
- **Salted repositories vs. file-hash verification.** A file hash is finalized with a repository salt, and nothing on the download path tells us what that salt is — the token and reconstruction responses carry no such field. Verification therefore assumes the default zero salt, which is right for everything I can test against (the reference file verifies). If salted repos exist in the wild, they'd fail verification with intact data. Options: leave it on and let the (explicit) error explain, or default `VerifyFileHash` to off. I've left it on.
- Should the live tests run on a CI schedule (nightly, say) rather than only on demand? They need no secrets, but they do depend on a public repo staying put.
- `XetClient` currently owns one `HttpClient` with redirects off, used for the Hub, CAS and CDN alike. That is why it works today — no CDN in the path redirects — but a single knob for all three is a bet. Two clients (Hub without redirects, data with) is the alternative if you'd rather be defensive.
