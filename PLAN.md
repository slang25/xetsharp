# XetSharp — Implementation Plan

Goal: a modern, high-performance, idiomatic C# client for the [Xet protocol](https://huggingface.co/docs/xet/main/en/index) (spec v1.1.0), able to download and upload files on the Hugging Face Hub interoperably with the Rust reference implementation ([xet-core](https://github.com/huggingface/xet-core)).

## Guiding principles

- **Verification first.** The spec's core promise is determinism: independent implementations MUST produce identical hashes, objects and API behaviour. Every layer gets a verification suite before (or alongside) its implementation, cross-checked against xet-core.
- **Bottom-up layering.** Each layer is pure and independently testable; network I/O only enters at the CAS client layer.
- **Idiomatic, modern .NET.** `net10.0`, nullable enabled, `Span<T>`/`IBufferWriter<byte>`-based parsing, `System.IO.Pipelines` where it pays, AOT-compatible, no reflection-based serialization in hot paths.
- **TUnit** for all tests; property-based tests where the spec defines invariants (e.g. chunk boundaries), golden-file tests where it defines exact bytes.

Detailed protocol digests (constants, binary layouts, endpoint schemas, gotchas) distilled from the spec live in [docs/protocol-notes/](docs/protocol-notes/).

## Protocol layers (bottom-up)

1. **Primitives** — `MerkleHash` (256-bit hash; canonical hex form byte-reverses each 8-byte group). ✅ walking skeleton
2. **Chunking** — gearhash-based content-defined chunking with the spec's table, mask, and min/target/max sizes. ✅ walking skeleton
3. **Hashing** — chunk hashes, xorb hashes (content-defined Merkle aggregation), file hashes (salted finalization), verification-range hashes, HMAC-keyed chunk hashes for dedup shards. ✅ walking skeleton
4. **Xorb format** — serialize/deserialize chunks with per-chunk headers and compression (none / LZ4 / byte-grouped LZ4). ✅
5. **Shard format** — binary shard reader/writer: header, file-info section, CAS-info section, footer, HMAC key handling. ✅
6. **CAS API client** — typed `HttpClient`-based client: token acquisition/refresh from the Hub, reconstruction endpoint, global-dedupe chunk query, xorb upload, shard upload; retry/backoff and error semantics per spec. ✅
7. **Download pipeline** — file ID → reconstruction → parallel ranged fetches of xorb data → decompress → reassemble → verify file hash. Term-range caching. ✅
8. **Upload pipeline** — chunk → dedupe (local + global) → pack xorbs → build shard → upload xorbs then shard → commit via Hub. ✅
9. **Public API** — a small, discoverable surface (e.g. `XetClient.DownloadAsync(repo, path, destination)`, `UploadAsync`), `Microsoft.Extensions.*`-friendly (DI, `ILogger`, `IHttpClientFactory`) but not requiring it. ✅ `XetClient`, `XetClientOptions`, injectable `HttpClient`, `IProgress<XetProgress>` on every transfer, `ILogger` throughout, and `AddXetClient` in a separate DI package

## Verification suite strategy

Three rings, in order of feedback speed:

1. **Golden vectors (offline, fast).** xet-core's own test suite publishes cross-implementation vectors: 130 chunk-boundary cases (SplitMix64-seeded and edge-case pattern data) and 18 Merkle xorb/file-hash cases — all ported verbatim into the TUnit suite. Chunk-hash and range-hash vectors are generated by a checked-in blake3-only harness (`tools/vectors/`). CI needs no Rust toolchain. The format layer adds golden files from the `xet-team/xet-spec-reference-files` dataset: all four shard variants, the 796-chunk listing, and a 10-chunk prefix of the real xorb (`tests/XetSharp.Tests/ReferenceFiles/`). The two artefacts too big to vendor — the 63 MB CSV and the whole 14 MB xorb — drive tests that opt in via `XETSHARP_REFERENCE_DIR`, and now include the upload path's strongest check: running the real CSV through chunking, packing and shard building reproduces the published upload-form shard **byte for byte**. The API layer adds sanitized *captured responses* (`tests/XetSharp.Tests/CapturedResponses/`): real reconstruction bodies for both API versions, including the multi-xorb and mid-chunk-range cases, so parsing is pinned to what the service actually sends.
2. **Property tests (offline).** Invariants from the spec: chunk sizes always within [min, max]; chunking is deterministic and content-defined (inserting data only shifts boundaries locally); round-trip xorb/shard serialize→parse; compression round-trips. The chunker also has a *differential* test against `NaiveChunker`, the rule written out exactly as the spec states it with no skipping ahead and no cleverness, over data shapes and block sizes the published vectors do not reach — which is what makes it safe to try optimising the loop the whole upload path runs through. The upload suite adds a whole-protocol round trip: a stand-in CAS service keeps the xorbs and shard an upload sends it and serves them back as a reconstruction, so files go up through the upload pipeline and come back down through the download pipeline with nothing in between the client did not produce.
3. **Live interop (online, opt-in).** Download a known file from a public Hub repo and byte-compare with the `resolve/` HTTP download; upload to a scratch repo and download it again. The download half is gated behind `XETSHARP_LIVE_TESTS=1` and needs no credentials — the Hub issues anonymous read tokens for public repos. `LiveDownloadTests` resolves, range-downloads (including a range straddling two xorbs) and byte-compares against the plain HTTP route, then downloads the whole 63 MB reference file and checks it against both its published file ID and its SHA-256. `LiveUploadTests` needs a repository to write to, so it is gated separately on `XETSHARP_LIVE_UPLOAD_REPO` plus a Hub token with write access; it uploads, commits, downloads and byte-compares, then removes what it wrote.

## Milestones

- **M0 — Walking skeleton** ✅: solution + TUnit harness; `MerkleHash`; gearhash chunker; chunk/xorb/file/verification hashing; 162 tests proving bit-identical output vs xet-core reference vectors.
- **M2 — Formats** ✅ *(taken before M1: the download pipeline has to parse xorb chunk records anyway, so the pure format layer is the cheaper thing to nail down first)*: xorb serializer/reader with all three compression schemes; MDB shard reader/writer round-tripping all four published reference shards byte for byte; HMAC chunk matching for dedupe responses. 212 tests.
- **M1 — Download** ✅: file-ID resolution off the resolve endpoint's redirect; a token cache that refreshes 30 s early and re-mints on a CAS `401`; `/v2/reconstructions` with `/v1` fallback; signed multi-range xorb fetches with a `multipart/byteranges` reader; ordered term assembly that decompresses chunk by chunk (so a term costs its *compressed* size in memory, not what it expands to) with bounded look-ahead prefetching; per-term `unpacked_length` checks plus whole-file hash and SHA-256 verification. 301 tests, four of them live against the Hub — the 63 MB reference file downloads and re-hashes to the file ID xet-core published for it.
- **M3 — Upload** ✅: chunk → deduplicate (within the upload and against the global index, HMAC-keyed matching and all) → pack xorbs measured against the 64 MiB ceiling rather than estimated → upload them, bounded and concurrent → build one shard with per-term verification hashes and the SHA-256 a Git repo's LFS pointer needs → send it only once every xorb it names is stored. Plus the Hub commit that publishes the result. 363 tests: the upload round-trips through the download pipeline, and the 63 MB reference file produces the very shard xet-core uploaded for it, byte for byte.
- **M4 — Performance & polish** ✅: BenchmarkDotNet suites over every per-byte path (chunking, hashing, xorb serialization, shard writing) with a throughput column; `IProgress<XetProgress>` on every download and upload; `ILogger` at the token, request, xorb and transfer seams, silent unless a factory is handed in; `AddXetClient` in a separate `XetSharp.Extensions.DependencyInjection` package; NuGet packaging with SourceLink, symbols, XML docs and the README in the package. The gearhash loop was measured rather than optimised on faith, and the measurement said to leave it alone; the same measurement said to parallelize xorb packing, which is now done and made an uploaded byte **2.3x cheaper** — see below. Transfer concurrency got the same treatment last: rather than tune it against a stand-in service, `sweep` downloads real bytes from the real Hub at each setting, and what it measured says to leave the defaults alone too — see below. 408 tests.

## Decisions taken (flag if you disagree)

- **BLAKE3** via the `Blake3` NuGet package (xoofx — native SIMD bindings, the fastest managed option). A pure-managed fallback could come later if the native dependency is a problem.
- **`net10.0` only** to start; multi-targeting (e.g. `netstandard2.0` for older consumers) deferred until the API stabilises.
- **CPM + slnx**, warnings as errors, AOT-compatible library.
- Test vectors are **vendored** (generated from xet-core by a checked-in harness) rather than generated at test time, keeping CI free of a Rust toolchain.
- **LZ4** via `K4os.Compression.LZ4.Streams` — the only maintained managed LZ4 for .NET, and the *frame* API is the one that matters (see below). Pure managed, so AOT stays fine.
- **No new dependencies for the HTTP layer**: `System.Text.Json` source generation (so no reflection, AOT intact), a plain `DelegatingHandler` for retry rather than Polly, and a hand-written `multipart/byteranges` reader. `IHttpClientFactory` users pass their own `HttpClient` through `XetClientOptions`; nothing requires `Microsoft.Extensions.*`.
- **`HEAD`, not `GET`, on the resolve endpoint.** The spec says `GET`, but with redirects disabled a file that is *not* on Xet answers with its whole body. `HEAD` returns the same Xet headers and never downloads anything by accident.
- **Whole-file downloads verify twice**: the chunks are re-aggregated into a file hash and compared to the file ID, and the written bytes are checked against the Hub's `X-Linked-Etag` SHA-256. Both are on by default and can be turned off in `XetDownloadOptions`. Partial downloads verify per-term `unpacked_length` only — the other two are not computable from a slice.
- **Xorbs are packed against a measured size, not an estimated one.** Each chunk is compressed as it is added, so the serialized length is always known. The raw cap is 64 MiB minus one 8-byte header per chunk at the 8192-chunk cap, which makes it *impossible* to build a xorb the service rejects — rather than discovering it one chunk too late and having to unwind.
- **`chunk_byte_range_start` is written as an uncompressed offset**, following the published upload-form shard rather than the field's name. The reference-file test would fail loudly if that were wrong.
- **Global-dedupe eligibility is `chunk_hash mod 1024 == 0`**, matching xet-core, so two clients ask about the same chunks and a hit is likely to cover a long run. The rate is internal, not a public knob; `UseGlobalDeduplication` turns the whole thing off.
- **Upload takes a batch of files and writes one shard.** Chunks pack across file boundaries, as the spec recommends, and one commit publishes the lot. A batch describing more than a 64 MiB shard throws rather than splitting — at 48 bytes per chunk record that is around 85 GB of data, past anything the Hub accepts as a single file, so splitting can wait until something needs it.
- **Uploading and committing are separate calls.** `UploadAsync` stores and registers the bytes — the whole of the Xet protocol's job. `CommitAsync` writes the LFS pointer that makes a Git-backed repository show the file, which is the Hub's own API and not in the Xet spec at all. `UploadAndCommitAsync` does both for the common case.
- **No on-disk dedup cache.** xet-core keeps shards on disk and dedupes against them across runs; the spec makes that optional. Deduplication here is per upload plus the global index.
- **Chunks compress in parallel; the xorb is assembled in order.** `MaxCompressionParallelism`
  (default 4, or the core count if lower) is a cap on how many chunks are *outstanding*, enforced by
  refusing the next chunk until the oldest is appended — so it is a true cap on how many run at once,
  not a queue depth the thread pool is free to widen. Getting that wrong the first time made two
  workers look 3.6x faster than one, which is how a benchmark tells you your option does not mean
  what its name says. Setting it to 1 keeps the thread pool out of the packer entirely.
- **Progress is a parameter, not an option.** `IProgress<XetProgress>` is passed per call rather than set on `XetClientOptions`, because a progress bar belongs to one transfer and the options object is shared by every transfer a client makes. Reports come about once a megabyte plus one at the end, counted in bytes rather than on a clock so a test sees the same reports every run.
- **`TotalBytes` is null rather than guessed.** An upload only reports a total when *every* file in the batch can say how long it is; one unmeasurable stream in a batch makes the whole total null. A bar that jumps backwards is worse than no bar.
- **The library depends on `Microsoft.Extensions.Logging.Abstractions` and nothing else from that family.** Logging abstractions are effectively part of the platform and cost a consumer nothing when unused; DI and `IHttpClientFactory` are a separate `XetSharp.Extensions.DependencyInjection` package, so a console tool that news up a `XetClient` pulls in none of it.
- **Log levels are chosen for the person running a transfer**, not for someone debugging this library: Information for "a file downloaded" and "an upload registered", Debug for tokens, requests and xorbs, Trace for per-chunk detail, Warning only for something that went wrong and was recovered from (a retry).
- **XML documentation ships, but CS1591 does not fail the build.** Every non-obvious member is documented; a rule that *every* public member must be would only produce "Gets the count." on a member called `Count`.

## Corrections the reference bytes forced

The spec's prose was wrong or silent in four places, each caught by round-tripping real reference
artefacts rather than by reading. All four are written up in [docs/protocol-notes/xorb-and-shard-formats.md](docs/protocol-notes/xorb-and-shard-formats.md):

- Compression scheme `1` is the LZ4 **frame** format, not a bare LZ4 block.
- The reference xorb carries four trailing bytes (`XETB`) that no version of the spec mentions.
- A shard's `chunk_byte_range_start` holds uncompressed-stream offsets, not offsets into the serialized xorb.
- Both of the shard footer's "reserved" regions hold real fields, so zeroing them breaks round-tripping — and the SHA-256 in the file-metadata record is byte-swapped like every other hash.

## What live traffic corrected in turn

Building M1 against the real service turned up four more gaps between the spec pages and what the
Hub sends today. All are written up in [docs/protocol-notes/cas-api-and-flows.md §8](docs/protocol-notes/cas-api-and-flows.md#8-what-live-traffic-adds):

- The resolve response points at auth with a `Link: …; rel="xet-auth"` header. The `X-Xet-Cas-Url` / `X-Xet-Access-Token` headers an earlier note guessed at do not exist — but `X-Linked-Etag` does, and it is the file's SHA-256.
- The signed byte range is not the `X-Xet-Signed-Range` query parameter the spec's examples show; it lives inside the CloudFront `Policy` as a `ByteRange.ExpectedHeader` condition. Same rule — the `Range` header must match exactly — but a client cannot read it off the URL, and a `GET` with no `Range` is a 403 rather than a full download.
- The v1 `fetch_info` entry shape (`range` + `url` + `url_range`), which the spec names but never defines.
- Anonymous access is real: no Hub token at all yields a working read token for a public repository.

## What the upload path could not verify offline

The download path had an independent oracle for everything: the Hub serves the same bytes over its
plain HTTP route, and the reference dataset publishes the hashes. The upload path has one too — the
published shard for the 63 MB reference file, which this client now reproduces byte for byte — but
three links in the chain have no offline check, and only a run against a real scratch repository can
settle them. `LiveUploadTests` is written and waiting for a repository to point it at.

- **The Hub commit.** `POST /api/{type}s/{repo}/commit/{revision}` is the Hub's Git API, outside the
  Xet spec, so its body shape is taken from what the official client sends rather than from a
  document. The tests pin the shape this client produces; nothing yet proves the Hub accepts it.
  This is the least certain thing in the milestone.
- **Whether a deduplicated upload needs CAS info for the xorbs it did not create.** The spec says the
  shard's CAS-info section lists every *new* xorb, and this client lists exactly those — it could not
  do otherwise, since a dedupe response returns chunk hashes HMAC-protected. If the service turns out
  to want the listing for referenced-but-existing xorbs too, a deduplicated upload will come back 400.
- **`preupload`.** The official client calls `POST /api/{type}s/{repo}/preupload/{revision}` before
  uploading, to be told whether a file should go via LFS/Xet at all. This client does not: it would
  be a second guessed-at endpoint, and the commit works without it as far as the documentation goes.

## What the benchmarks said

Where an uploaded byte's time actually goes, on an M-series Mac (`--job short --inProcess`, so
every case gets the same class of core):

| Stage | Throughput |
| --- | --- |
| Gearhash boundary scan alone | 1,500 MB/s |
| Chunking, allocation and all | 1,350 MB/s |
| BLAKE3 chunk hashing | 1,280 MB/s |
| **Xorb serialization, float32 weights** | **221 MB/s** |
| Xorb serialization, incompressible data | 767 MB/s |
| Xorb deserialization (the download side) | 723 MB/s |

The headline: **compression costs about six times what chunking and hashing cost together**, and it
is the only stage that is nowhere near memory speed. Every chunk is compressed twice — plain LZ4 and
byte-grouped LZ4 — because the format stores whichever came out smaller, and on the compressible
data this client exists to move, the byte-grouped attempt is the expensive one. Choosing between the
two more cheaply is not available: which scheme wins is part of what makes a xorb byte-identical to
the reference implementation's. Compressing several chunks at once is, and it changes no output
byte, so that is what M4 did.

### What parallel packing bought

`XorbBuilder` now hands each chunk's compression to the thread pool and appends the results **in the
order the chunks were added**, never the order they finished, with at most
`MaxCompressionParallelism` of them outstanding at a time. Same bytes, same hash, same object in the
CAS — the reference file still packs into the very shard xet-core published for it, and the whole
796-chunk file now packs identically at one worker and at four.

Per-degree, on the same M-series Mac (`--inProcess`, 15 iterations — see the note in
[benchmarks/README.md](benchmarks/README.md) about what a loaded machine does to this suite):

| Workers | Compression alone | + chunk hashing | + chunking (the whole upload CPU path) |
| --- | --- | --- | --- |
| 1 | 219 MB/s | 200 MB/s | **187 MB/s** |
| 2 | 444 MB/s | 420 MB/s | 294 MB/s |
| 4 | 851 MB/s | 820 MB/s | **423 MB/s** |
| 8 | 1,303 MB/s | 954 MB/s | 434 MB/s |

Two things fall out of the third column, which is the one that matters. It **flattens at four**, so
that is the default — past four the extra threads take cores from the rest of the process for about
2%. And what they are now waiting on is the calling thread: chunking, hashing and the read, which
this does not parallelize. The 32 MB of per-chunk arrays a 32 MiB buffer allocates, noted below as
the chunker's remaining cost, is a much more interesting number than it was when compression was
five times more expensive than everything around it.

The plan also called for a "SIMD-friendly gearhash inner loop". Measuring it first turned that into a
decision not to write one.

- **The scan is not where the time goes, and it is not latency-bound.** The one-byte-at-a-time loop
  runs at about 1.5 GB/s on an M-series Mac. Unrolling it four bytes at a time — which leaves only
  the `h << n` terms depending on the group before, and should in theory break a two-deep dependency
  chain per byte — measured **1.4x slower**. Both x86 and Arm64 already fold shift-and-add into one
  instruction (`lea`, `add ... lsl`), so there was no chain to break, and the extra shifts, adds and
  tests are pure cost. Reading the gear table through a raw reference rather than the span, to drop
  a bounds check that can never fail, made no measurable difference either.
- Both forms are kept in `GearhashScanBenchmarks` so the next person to have the idea can re-measure
  instead of taking this on trust, and the chunker carries a comment pointing at them.
- Verification came first here too: before any of this, the chunker gained a differential test
  against `NaiveChunker` — the rule written out exactly as the spec states it, one byte at a time —
  over data shapes and block sizes the published vectors do not reach. That test would have caught a
  boundary moved by a single byte, and it is what makes trying an optimisation cheap.
- Chunking a 32 MiB buffer allocates 32 MB: one array per chunk. That, not the hash loop, is the
  chunker's remaining cost, and removing it means handing chunks out as spans into the caller's read
  buffer — which the upload pipeline cannot use as it stands, because it awaits a deduplication
  query per chunk and a span cannot cross an `await`. Parallel packing has since given the same
  answer a second reason: a chunk is now read by a thread-pool worker after `AddAsync` returns, so
  its memory has to outlive the call whatever the chunker hands over. Left alone deliberately; it
  needs the upload loop restructured, not the chunker — and the restructuring would have to hand out
  slices of a buffer nobody overwrites until the xorb is sealed.

On an Apple Silicon Mac, BenchmarkDotNet's process-per-case model makes results bimodal — a case
scheduled onto an efficiency core reads about four times slower. All the figures above come from
`--inProcess` runs, where every case gets the same core class. This is written up in
[benchmarks/README.md](benchmarks/README.md).

### What the link said

Transfer concurrency was the last M4 item, and the objection to settling it was that a stand-in CAS
has neither of the two things concurrency exists to hide: the round trip before a range starts
arriving, and whatever ceiling one connection runs into. So the measurement moved to the real thing.
`dotnet run --project benchmarks/XetSharp.Benchmarks -c Release -- sweep` downloads the same public
bytes once per `MaxConcurrentDownloads` setting, rounds interleaved, timed against a plain
single-connection HTTP download of the same bytes as the link's own ceiling. No token, nothing
written, no Rust — it is the only measurement here that needs a network.

Two things came out of it, on 256 MiB of `openai-community/gpt2`'s weights over a domestic ~250
Mbit/s link — full numbers in [benchmarks/README.md](benchmarks/README.md#measuring-a-real-link):

- **The setting did not matter, because the link was already full.** Medians of 30, 30, 31 and 29
  MB/s at 1, 2, 4 and 8, against 23–27 MB/s for one plain HTTP connection, and the spread between
  rounds of the *same* setting reached 30%. One request in flight saturates a link this size. A
  measurement that cannot separate 1 from 8 cannot justify building something to choose between
  them, so **concurrency stays fixed** and adaptive tuning stays unwritten — the same answer, for the
  same reason, as the gearhash loop. What has changed is that re-opening it now costs one command on
  a fatter pipe rather than an argument.
- **`MaxConcurrentDownloads` is not what bounds requests in flight for a large file —
  `MaxBufferedBytes` is.** A file stored as full xorbs comes back in ~56 MB fetches, so the 128 MiB
  budget holds two of them however high the count is set. That is the right trade — each extra
  request in flight is another ~56 MB held in memory — but the option's name promised something it
  does not deliver on its own, so both options now say so. `sweep --plan` prints the fetch sizes and
  the resulting in-flight ceiling for any file, transferring nothing.

## Open questions for you

- Package identity: publish as `XetSharp` on NuGet when ready? The projects are packable now — `dotnet pack -c Release` produces `XetSharp` and `XetSharp.Extensions.DependencyInjection`, both at `0.1.0` with symbols and SourceLink — but nothing publishes them. A release workflow (tag → pack → push) is a small job once you've decided on the identity and where the API key lives.
- Any interest in a `netstandard2.0`/`net8.0` multi-target early (e.g. for use inside other tools), or is `net10.0`-only fine for now?
- **Two packages or one?** `AddXetClient` lives in `XetSharp.Extensions.DependencyInjection` so the core library needs nothing from `Microsoft.Extensions.*` but the logging abstractions. The alternative — putting it in the main package — costs every consumer a dependency on `Microsoft.Extensions.Http` and everything under it. Easy to collapse into one package if you'd rather have the smaller matrix.
- **Adaptive concurrency — measured, and left fixed.** `sweep` now runs against the real Hub, and on a ~250 Mbit/s link every setting from 1 to 8 lands inside the noise, because one request already fills the link (see *What the link said*). That is an answer, but it is an answer from the wrong link: it says nothing about a machine with 10 Gbit to the CDN, which is where adaptive tuning would earn its keep. Worth running `sweep` from a cloud VM before deciding, or happy to close it as done?
- **How many of a host's cores should a library take by default?** Packing now uses four threads unless told otherwise, which is the fastest setting for a process doing nothing else and an opinion imposed on a process that is. The alternatives are 1 (fastest is opt-in), `ProcessorCount` (fastest by default, rudest), or reading it off the number of files being uploaded. Happy to change it — this is the only place XetSharp spends cores it was not explicitly given.
- The shard footer fields above are undocumented; I've surfaced the byte-count totals on `ShardFooter` so shards round-trip, and reject shards carrying lookup tables (which this library never writes). Happy to make that lenient instead if you'd rather parse everything xet-core can emit.
- **The upload side of that measurement has no oracle at all.** `MaxConcurrentUploads = 4` was never measured, and cannot be without somewhere to write — `sweep` is download-only because a public repo is readable and nothing is writable. If the scratch repository below appears, the same treatment is a small addition to the same tool.
- **Salted repositories vs. file-hash verification.** A file hash is finalized with a repository salt, and nothing on the download path tells us what that salt is — the token and reconstruction responses carry no such field. Verification therefore assumes the default zero salt, which is right for everything I can test against (the reference file verifies). If salted repos exist in the wild, they'd fail verification with intact data. Options: leave it on and let the (explicit) error explain, or default `VerifyFileHash` to off. I've left it on.
- **A scratch repository to point the live upload tests at.** Everything above the commit is verified offline; the commit is not verified at all. If you make (or name) a throwaway repo with write access from your Hub token, `XETSHARP_LIVE_UPLOAD_REPO=you/xetsharp-scratch dotnet run --project tests/XetSharp.Tests` settles all three of the open items in one run.
- **Term fragmentation on deduplication.** A global-dedupe hit is taken wherever it lands, even for a single chunk, which can leave a reconstruction with many short terms — and a download pays per term. xet-core targets an average of 8 chunks per term and declines matches shorter than that. Worth adding a minimum-run rule, or leave it greedy until a benchmark says otherwise?
- Should the live tests run on a CI schedule (nightly, say) rather than only on demand? The download ones need no secrets, but they do depend on a public repo staying put; the upload ones would need a token in CI.
- `XetClient` currently owns one `HttpClient` with redirects off, used for the Hub, CAS and CDN alike. That is why it works today — no CDN in the path redirects — but a single knob for all three is a bet. Two clients (Hub without redirects, data with) is the alternative if you'd rather be defensive.
