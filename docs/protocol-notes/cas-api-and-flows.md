## 1. Authentication (Hub → Xet token)

The Xet CAS server uses **bearer authentication** with a token generated by the Hugging Face Hub. A client MUST acquire the token **and** the CAS base URL before invoking any CAS API.

### Token request endpoint

```txt
GET https://huggingface.co/api/{repo_type}s/{repo_id}/xet-{token_type}-token/{revision}
```

Note the plural `s` after `{repo_type}` — the path segment is `models`, `datasets`, or `spaces`.

Path parameters (all required):

| Param | Values / meaning |
|---|---|
| `repo_type` | `model`, `dataset`, or `space` |
| `repo_id` | `namespace/repo-name` |
| `token_type` | `read` or `write` |
| `revision` | git branch, tag, or commit hash; default to `main` if no specific ref is required |

Required header: `Authorization: Bearer <HF Hub token>`

Example URLs (verbatim from spec):

```txt
https://huggingface.co/api/models/sentence-transformers/all-MiniLM-L6-v2/xet-read-token/main
https://huggingface.co/api/datasets/HuggingFaceM4/the_cauldron/xet-write-token/v1.1
https://huggingface.co/api/spaces/jsulz/ready-xet-go/xet-read-token/main
```

Example request (verbatim):

```http
GET /api/models/black-forest-labs/FLUX.1-dev/xet-read-token/main
Host: huggingface.co
Authorization: Bearer xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

### Response

JSON object:

```typescript
{
   "accessToken": string,   // bearer token for all Xet CAS APIs
   "exp": number,           // unix timestamp when token expires
   "casUrl": string,        // API service endpoint base URL
}
```

Example (verbatim):

```json
{
   "accessToken": "xet_xxxxxxxxxxx",
   "exp": 1848535668,
   "casUrl": "https://cas-server.xethub.hf.co"
}
```

- Clients MAY assume `accessToken` and `casUrl` field lengths have an upper limit of **64000 characters**.
- **Refresh**: use the same API to generate a new token. `xet-core` refreshes with a **30-second buffer** before `exp`. Tokens SHOULD be refreshed/swapped before expiration; a `401` from the CAS API means refresh and retry.

### Token-endpoint errors

- `401 Unauthorized`: invalid or missing Hub authentication token
- `403 Forbidden`: insufficient permissions for the requested token type
- `404 Not Found`: repository or revision does not exist

### Token scope

- Scopes: `read` and `write`. `write` supersedes `read` (a write token can call all read APIs).
- Only the upload APIs (`POST /v1/xorbs/...`, `POST /v1/shards`, `POST /v2/shards`) require `write`; everything else needs `read`.
- Scope is **limited to the repository and ref for which the token was issued**. Different repos or different branches require different tokens.
- To get a `write` Xet token, the Hub token used MUST have write access to that repo+ref; for `read`, at least read access. Fine-grained Hub tokens MUST have read/write access to repo *contents*.
- Security: tokens are time-limited; SHOULD NOT be logged; prefer read tokens, request write only when needed.

### Anonymous access

The spec lists the `Authorization` header as **required** on the token endpoint and does not document anonymous/unauthenticated access. *(Implementation note, not from these spec pages: the official `huggingface_hub`/`hf-xet` clients successfully obtain read tokens for public repos without a Hub token — the Hub issues an anonymous-scoped Xet read token. A C# client should attempt the token request without `Authorization` for public-repo reads and treat 401 as "credentials required", but this behavior is not normatively guaranteed by the spec.)*

## 2. File ID resolution (Hub file → Xet file ID)

Build the resolve URL:

```txt
https://huggingface.co/{namespace}/{repository}/resolve/{branch}/{filepath}
```

Example: `https://huggingface.co/Qwen/Qwen-Image-Edit/resolve/main/transformer/diffusion_pytorch_model-00001-of-00009.safetensors`

- Make a `GET` request to the resolve URL using standard Hub credentials/token.
- If the file is stored on Xet, a successful response carries the **`X-Xet-Hash`** header. Its string value **is the Xet file ID** — already in string (hex) representation, usable directly in the reconstruction API path.
- The resolve URL returns a **302 redirect**; following it downloads via the legacy LFS-compatible route. To use the Xet protocol you **MUST NOT follow the redirect** (issue the request with auto-redirect disabled; in .NET, `HttpClientHandler.AllowAutoRedirect = false`).
- The spec page documents only `X-Xet-Hash`. *(An earlier implementation note here guessed that the Hub also emits `X-Xet-Cas-Url` / `X-Xet-Access-Token` / `X-Xet-Token-Expiration` / `X-Xet-Refresh-Route`. Live traffic says otherwise — see [§8](#8-what-live-traffic-adds).)*

## 3. CAS API — general rules

Base URL = `casUrl` from the token response. All endpoints: `Authorization: Bearer <accessToken>`.

### Hash-to-string conversion (critical, easy to get wrong)

Hashes (32 bytes) appear in API paths as 64 lowercase hex characters, but you **MUST NOT** hex-encode the bytes directly.

Procedure: for each 8-byte region (indices 0–7, 8–15, 16–23, 24–31), **reverse the byte order within the region**, then concatenate and hex-encode. Equivalently: treat each 8-byte region as a **little-endian u64** and concatenate the four hex representations, each zero-padded to 16 chars.

Example (verbatim): hash bytes `[0,1,2,...,31]` reorder to `[7,6,5,4,3,2,1,0, 15,...,8, 23,...,16, 31,...,24]`, so the string is **not** `000102...1f` but `07060504030201000f0e0d0c0b0a0908171615141312111f1e1d1c1b1a1918`.

This conversion applies **every time** a hash is represented as a string (reconstruction paths, xorb upload paths, global-dedupe paths, JSON keys/values).

### Error semantics (all endpoints)

Non-retryable:

- `400 Bad Request` — invalid parameters (malformed hash/file_id; invalid xorb/shard body on uploads). Fix before retrying.
- `401 Unauthorized` — refresh the token (or supply one) and continue.
- `403 Forbidden` — token scope too narrow (e.g. `read` token on a `write` API). Retry with a `write`-scope token.
- `404 Not Found` — resource (xorb/file/chunk) does not exist on GET/HEAD APIs.
- `416 Range Not Satisfiable` — reconstruction APIs only; requested range start ≥ file length.

Retryable:

- Connection errors — retry if intermittent; ensure no firewall blocks; SHOULD NOT use DNS overrides.
- `429` — back off, lower request rate, wait and retry. **Assume all APIs are rate limited.**
- `500` — intermittent server issue; retry.
- `503` — temporarily unavailable; wait and retry.
- `504` — gateway timeout; wait and retry.

Use exponential backoff for transient failures.

## 4. CAS API — endpoints

### 4.1 GET /v2/reconstructions/{file_id} — Get File Reconstruction (recommended default)

- Method: `GET`. Min scope: `read`. Body: none.
- `file_id`: file hash, 64 lowercase hex chars (via hash-to-string procedure).
- Headers:
  - `Range` (optional): `bytes={start}-{end}`, end **inclusive**.
  - `Accept-Encoding` (optional): server supports `gzip` and `zstd` on the JSON response; clients SHOULD send one to shrink large reconstruction responses.
- Response: JSON `QueryReconstructionResponse` (v2 shape):

```json
{
  "offset_into_first_range": 0,
  "terms": [...],
  "xorbs": {...}
}
```

- Errors: `400` malformed file_id; `401`; `404` file does not exist (not retryable); `416` range start beyond EOF (not retryable).
- Fallback: older CAS deployments may not serve `/v2/`; on `404` or `501` clients SHOULD fall back to deprecated `GET /v1/reconstructions/{file_id}`. (Note: this makes 404 ambiguous — v1 fallback then distinguishes "endpoint missing" from "file missing".)

```txt
GET /v2/reconstructions/0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
-H "Authorization: Bearer <token>"
OPTIONAL: -H Range: "bytes=0-100000"
```

### 4.2 GET /v1/chunks/{prefix}/{hash} — Query Chunk Deduplication (Global Dedupe)

- Method: `GET`. Min scope: `read`. Body: none.
- `prefix`: MUST be `default-merkledb` (only acceptable value).
- `hash`: chunk hash, 64 lowercase hex chars.
- Response: **shard-format bytes** (`application/octet-stream`) — deserialize per the shard spec (global-deduplication variant).
- Errors: `400` malformed hash; `401`; `404` chunk not tracked by global dedup (not retryable, and an expected/normal outcome).
- Example response body reference file: `https://huggingface.co/datasets/xet-team/xet-spec-reference-files/blob/main/Electric_Vehicle_Population_Data_20250917.csv.shard.dedupe`

### 4.3 POST /v1/xorbs/{prefix}/{hash} — Upload Xorb

- Method: `POST`. Min scope: `write`.
- `prefix`: MUST be `default`.
- `hash`: xorb hash, 64 lowercase hex chars.
- Body: serialized xorb bytes (`application/octet-stream`), per the xorb format spec.
- Response: JSON `UploadXorbResponse`:

```json
{
  "was_inserted": true
}
```

`was_inserted: false` means the xorb already existed — **not an error** (idempotent).

- Errors: `400` malformed hash / hash doesn't match body / bad serialization; `401`; `403` scope too narrow (MUST retry with `write` token).
- Example request body reference file: `https://huggingface.co/datasets/xet-team/xet-spec-reference-files/blob/main/eea25d6ee393ccae385820daed127b96ef0ea034dfb7cf6da3a950ce334b7632.xorb`

### 4.4 POST /v1/shards — Upload Shard

- Method: `POST`. Min scope: `write`. Path has no parameters.
- Body: serialized shard bytes (`application/octet-stream`), per the shard format spec (shard-upload variant). Uploads file reconstructions + new-xorb listing; **marks the files as uploaded**.
- Response: JSON `UploadShardResponse`:

```json
{
  "result": 0
}
```

`result`: `0` = shard already exists; `1` = `SyncPerformed` (registered). The value carries no actionable meaning — a `200 OK` means the upload succeeded and the listed files are considered uploaded.

- Errors: `400` shard incorrectly serialized or failed verification — can mean a **referenced xorb doesn't exist** or the **shard is too large**; `401`; `403` scope too narrow.
- Example request body reference file: `https://huggingface.co/datasets/xet-team/xet-spec-reference-files/blob/main/Electric_Vehicle_Population_Data_20250917.csv.shard.verification-no-footer`

### 4.5 POST /v2/shards — Streaming Shard Upload

- Same validation/registration as `/v1/shards`, same request body, min scope `write`.
- Response: newline-delimited JSON stream (`Content-Type: application/x-ndjson`, `Cache-Control: no-cache`), one event per line.
- **HTTP status is `200 OK` as soon as the stream starts** — success/failure is carried by the terminal event, NOT the status code. Clients MUST read the stream to completion and inspect the terminal event.
- Event types (discriminated by `type`):
  - `validating` — progress: `{"type":"validating","verified":120,"total":512}`. `total` grows while the shard is still being received; treat `verified/total` as a live ratio, not a final percentage.
  - `committing` — durable write in progress: `{"type":"committing","stage":"uploading"}`. `stage` is `uploading` (persisting shard object to storage) or `syncing` (registering shard: file ids, global dedup, shard list).
  - `result` — terminal success: `{"type":"result","result":1}`. Same values as `UploadShardResponse` (`0` existed, `1` registered); a `result` event means success.
  - `error` — terminal failure with sanitized message: `{"type":"error","message":"..."}`. The only failure signal once streaming has started.
- Typical successful stream (verbatim):

```txt
{"type":"validating","verified":0,"total":512}
{"type":"validating","verified":256,"total":512}
{"type":"committing","stage":"uploading"}
{"type":"committing","stage":"syncing"}
{"type":"result","result":1}
```

- If validation stalls, the server periodically re-emits the last progress event as a **heartbeat**, so clients can keep a short read timeout.
- Pre-stream failures still use normal HTTP errors (`401`, `403`, malformed request).
- Additive change: clients SHOULD try `/v2/shards` and fall back to `/v1/shards` on `404 Not Found`.

### 4.6 POST /v1/reconstructions — Batch File Reconstruction

- Method: `POST`. Min scope: `read`. Header `Content-Type: application/json`; optional `Accept-Encoding: gzip`/`zstd`.
- Body: JSON array of keys `{ "prefix", "hash" }`; `prefix` is `default`; `hash` is the file hash (64 hex chars). Duplicate keys are de-duplicated server-side.

```json
[
  { "prefix": "default", "hash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef" }
]
```

- Response: JSON `BatchQueryReconstructionResponse`:

```json
{
  "files": {
    "0123...": [/* CASReconstructionTerm, ... */]
  },
  "fetch_info": {
    "0123...": [/* CASReconstructionFetchInfo, ... */]
  }
}
```

`files` maps file id → reconstruction terms; `fetch_info` is **shared across files, keyed by xorb hash**. Returns the **v1** response shape; for the multi-range-optimized format call `/v2/reconstructions/{file_id}` per file.

- Errors: `400` malformed body/invalid file id; `401`; `404` one or more files do not exist (not retryable).

### 4.7 HEAD /v1/xorbs/{prefix}/{hash} — Head Xorb

- Existence check. Min scope: `read`. `prefix` = `default`. Empty body response; `Content-Length` response header = stored xorb size in bytes.
- Errors: `400`, `401`, `404` (xorb doesn't exist, not retryable).

### 4.8 HEAD /v1/files/{file_id} — Head File

- Existence check. Min scope: `read`. Empty body; `Content-Length` = full file size in bytes.
- Errors: `400`, `401`, `404`.

### 4.9 GET /v2/file-chunk-hashes/{file_id} — Get File Chunk Hashes (delta uploads)

- For a file plus a set of "dirty" byte ranges (regions the client intends to re-chunk), returns the chunk windows to re-chunk plus opaque hash subtrees for the unchanged gaps, so a delta upload can compose a new shard without re-uploading known chunks. Response covers the full file.
- Method: `GET`. Min scope: `read`.
- Headers:
  - `X-Range-Dirty` (REQUIRED): one or more byte ranges, standard `bytes=` syntax, inclusive ends, comma-separated, e.g. `bytes=0-1023,5000-9999`. Sorted/merged server-side. At least one range MUST be present.
  - `Accept-Encoding` (optional): `gzip`/`zstd`.
- Response: JSON `FileChunkHashesResponse` — **uses `camelCase` field names, unlike other endpoints**:

```json
{
  "totalChunks": 1234,
  "fileSize": 9876543,
  "windows": [
    { "dirtyByteRange": [0, 65536] }
  ],
  "hashRanges": [
    null,
    "<opaque MerkleHashSubtree>"
  ],
  "gapVerification": [
    "<hex MerkleHash>"
  ]
}
```

- `windows`: one per dirty range (adjacent dirty ranges sharing a chunk are merged). `dirtyByteRange` is `[start, end)` — **exclusive end** (while the request header uses inclusive ends). Bounds are chunk-aligned, expanded outward to fully contain the dirty range; client re-chunks exactly this span.
- `hashRanges`: `N + 1` entries for `N` windows — `[before_w0, between_w0_w1, ..., after_wN]`; each an opaque `MerkleHashSubtree` passed as-is to the client merge routine; `null` when the gap is empty (e.g. window starts at chunk 0).
- `gapVerification`: one hash per stable original segment (fully inside a gap, in segment order); client wraps each into a `FileVerificationEntry` in the composed shard's verification section. Empty when every segment overlaps a dirty range.
- Errors: `400` missing/malformed `X-Range-Dirty`, malformed file_id, or no range survives clamping; `401`; `404`.

```txt
GET /v2/file-chunk-hashes/0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
-H "Authorization: Bearer <token>"
-H "X-Range-Dirty: bytes=0-65535,200000-299999"
```

### 4.10 GET /v1/reconstructions/{file_id} — Get File Reconstruction (v1, DEPRECATED)

- Same as v2 but returns the v1 shape (`terms` + `fetch_info` instead of `xorbs`). Still served for existing clients; will be removed. Use as fallback when `/v2/` returns `404`/`501`.
- Optional `Range: bytes={start}-{end}` (inclusive end). Min scope `read`.
- Response:

```json
{
  "offset_into_first_range": 0,
  "terms": [...],
  "fetch_info": {...}
}
```

- Errors: `400`, `401`, `404`, `416` — same semantics as v2.

## 5. Download protocol (step-by-step)

Two stages: (1) reconstruction query, (2) data fetch + reassembly.

### Stage 1 — Reconstruction query

- Requires at least a `read`-scope Xet token.
- `GET {casUrl}/v2/reconstructions/{file_id}` with optional `Range` header.
- For large files it is RECOMMENDED to request the reconstruction in batches (e.g. first 10 GB via `Range`, download, then the next 10 GB, etc.).

### Stage 2 — QueryReconstructionResponse (v2) structure

Simple example (verbatim):

```json
{
  "offset_into_first_range": 0,
  "terms": [
    {
      "hash": "a1b2c3d4e5f6789012345678901234567890abcdef1234567890abcdef123456",
      "unpacked_length": 263873,
      "range": {
        "start": 0,
        "end": 4
      }
    }
  ],
  "xorbs": {
    "a1b2c3d4e5f6789012345678901234567890abcdef1234567890abcdef123456": [
      {
        "url": "https://transfer.xethub.hf.co/xorb/default/a1b2c3d4e5f6789012345678901234567890abcdef1234567890abcdef123456?X-Xet-Signed-Range=bytes%3D0-131071&Expires=1735689600&Policy=eyJTdGF0ZW1lbnQiOlt7IlJlc291cmNlIjoidHJhbnNmZXIueGV0aHViLmhmLmNvL3hvcmIvZGVmYXVsdC9hMWIyYzNkNCoiLCJDb25kaXRpb24iOnsiRGF0ZUxlc3NUaGFuIjp7IkFXUzpFcG9jaFRpbWUiOjE3MzU2ODk2MDB9fX1dfQ__&Signature=Kx8n2rJ5pYqWc3vLdBhTfZ9mAeRsUgN1oiXwEbCa0kqLm4t7yHpV6dZ~woIsPuGj&Key-Pair-Id=K2EXAMPLECDNKEY01",
        "ranges": [
          {
            "chunks": { "start": 0, "end": 4 },
            "bytes": { "start": 0, "end": 131071 }
          }
        ]
      }
    ]
  }
}
```

Fields:

- `offset_into_first_range` (`number`): `0` for full-file or range starting at 0. For range queries: byte offset into the **first term's decompressed data** to start keeping bytes from (data MUST be downloaded in full chunks; requested range may start mid-chunk — the skip may span multiple chunks within the first term).
- `terms` (`Array<CASReconstructionTerm>`): ordered list. Each term:
  - `hash`: xorb hash (64-char lowercase hex string)
  - `range`: chunk index range `{ start, end }`, **end-exclusive** `[start, end)`
  - `unpacked_length`: expected total decompressed length of the term's chunks (for validation)
- `xorbs` (`Map<xorb-hash-hex, Array<XorbMultiRangeFetch>>`): typically 1 entry per xorb; multiple only when the URL would exceed the URL length limit. Each `XorbMultiRangeFetch`:
  - `url`: signed URL with all byte ranges encoded in `X-Xet-Signed-Range` (URL-encoded, e.g. `bytes%3D0-131071`) plus CDN signature params (`Expires`, `Policy`, `Signature`, `Key-Pair-Id`). Short-lived; **do not cache or rewrite**.
  - `ranges`: `Array<XorbRangeDescriptor>` ordered by ascending `chunks.start` (equivalently ascending `bytes.start`). Each descriptor:
    - `chunks`: `{ start, end }` — **end-exclusive**
    - `bytes`: `{ start, end }` — **end-inclusive**, used verbatim in the HTTP `Range` header

IMPORTANT: the signed URL authorizes **exactly** the byte ranges in its `X-Xet-Signed-Range` set; requesting bytes outside that set returns an authorization failure. Clients SHOULD request all ranges of one `XorbMultiRangeFetch` in a **single request** — the response is `multipart/byteranges` when there is more than one range.

### Stage 3 — Download and reconstruct

1. For each entry in `xorbs`, issue one multi-range `GET` per fetch entry:
   - `Range: bytes=s1-e1,s2-e2,...` built from `bytes` ranges in the given (ascending) order — must match the `X-Xet-Signed-Range` value. Omitting or altering the `Range` header ⇒ authorization failure.
   - Single range ⇒ `206 Partial Content` with raw xorb bytes.
   - Multiple ranges ⇒ `206 Partial Content` with `Content-Type: multipart/byteranges`; parse each part.
   - Each part is a forward reader over serialized xorb data: deserialize chunks sequentially (chunk indices `chunks.start .. chunks.end-1`); the part should be fully consumed at the end.
2. Process `terms` in order using the downloaded chunks.
3. **Verification (MUST)**: for each term, the combined **decompressed** length of its chunks MUST equal the term's `unpacked_length`; otherwise reject the reconstruction (truncated/corrupt xorb data).
4. For the first term only, skip `offset_into_first_range` bytes (the skip can consume whole chunks: decrement across chunks until it fits within one, then slice).
5. Concatenate term outputs in term order to produce the file.
6. Range requests: truncate the assembled output to the requested length (range end may fall mid-chunk). Exception: if the requested range exceeds file length, the returned content is already shorter — no truncation needed.

Chunks may be reused across terms (dedup): e.g. terms `[1,4)` and `[3,43)` from the same xorb both use chunk index 3 — download once, use twice. Cache downloaded chunks keyed by `(xorb_hash, chunk_index)`.

### Concurrency, caching, retries (download)

- Xorb data MAY be downloaded in parallel, but **terms MUST be assembled in order** (or written at computed offsets on seekable outputs — spec explicitly allows multi-threaded writes at different offsets).
- Clients MAY interleave downloading and term processing to reduce memory; no need to download all xorb data first.
- `xet-core` uses adaptive concurrency (scale up with bandwidth, back off under congestion).
- Caching: do not cache reconstruction objects (signed URLs are short-lived and you must re-call the API anyway); cache chunks **by range** rather than individually; caching only pays off for repeated/similar content.
- Retry: exponential backoff for transient failures (429/500/503/504/connection errors).

## 6. Upload protocol (step-by-step)

Pipeline: file → chunks → dedup → xorbs → upload xorbs → shards → upload shards. All steps can run concurrently **except** the shard-after-xorbs ordering rule below.

### Object model

- **Chunk**: slice of file data. Target ~64 KiB; max 128 KiB; min 8 KiB (min not enforced for the last chunk of a file or files < 8 KiB). Boundaries from the content-defined chunking algorithm (see `chunking` spec); hash from `hashing#chunk-hashes`.
- **Xorb**: sequence of chunks, compressed and serialized after a header (see `xorb` spec). Always ≤ **64 MiB** serialized; ~1024 chunks on average (variable). Chunks addressed by 0-based index; ranges are end-exclusive `[0, 100)`. Xorb hash per `hashing#xorb-hashes`.
- **File reconstruction**: ordered series of terms, each = (xorb hash, chunk index range). Reconstruct by concatenating decompressed chunks in term order.
- **Shard**: serialized file-info (reconstructions) + CAS-info (xorb metadata) per `shard` spec. Uploading a shard registers files as uploaded. Also used as the wire format for global-dedupe responses. `xet-core` also uses the shard format as a local dedup cache (optional for other implementations).

### Steps

1. **Chunking** — split file with the content-defined chunking algorithm; compute each chunk's hash (used for dedup).
2. **Deduplication (OPTIONAL optimization)** — for each chunk hash, check: (a) chunks already seen in the current upload, (b) a local cache of known chunks, (c) the Global Dedup API `GET /v1/chunks/default-merkledb/{chunk_hash}`. Deduplicated chunks SHOULD NOT be re-uploaded (not included in a new xorb); the file reconstruction instead references the existing xorb + chunk index. Global-dedupe eligibility in `xet-core`: queried for chunks where `chunk % 1024 == 0` (per the spec's sequence diagram — i.e. sampled, not every chunk).
3. **Xorb formation & hashing** — collect contiguous runs of chunks into xorbs (~64 MiB each), preserving order within runs; compute xorb hash from its chunks.
4. **Xorb serialization & upload** — serialize per xorb format; `POST /v1/xorbs/default/{xorb_hash}` with `write` token. A xorb MUST be uploaded before any shard referencing it.
5. **Shard formation** — map each file to a reconstruction over available xorbs (dedup terms may reference pre-existing CAS xorbs). Per file:
   - compute the file hash (`hashing#file-hashes`) — this becomes the file ID;
   - compute a **term verification hash** for each term (`hashing#term-verification-hashes`) — proves the uploader actually has the file data;
   - optionally compute the **SHA256 of the file contents** — REQUIRED for Git-based Hub repos (models/datasets/Spaces) because their LFS pointer files reference the SHA256; not needed for Storage Buckets.
   - Collect metadata for each **new** xorb: xorb hash; hash and length of every chunk; serialized xorb length; sum of chunk lengths. This fills the shard's file-info and CAS-info sections.
6. **Shard serialization & upload** — serialize the shard for the batch of files; `POST /v1/shards` (or streaming `POST /v2/shards`, falling back to v1 on 404). Success (`200 OK` / `result` event) registers the files as uploaded. If a serialized shard would exceed **64 MiB**, you MUST split into multiple shards.

**Done**: after all xorbs and all shards upload successfully, the upload is complete and any client can download via the download protocol. For Git-based Hub repos, the user must then **commit a git LFS pointer file** containing the file's SHA256 (not required for Storage Buckets).

### Ordering & concurrency

- Natural ordering: chunk boundary → chunk hash; chunk collection → xorb hash; etc.
- **Enforced rule: all xorbs referenced by a shard MUST be uploaded before that shard is uploaded.** The server rejects a shard upload (400) if any referenced xorb is missing. "Referenced" = any xorb hash appearing in the CAS-info section or in file-info data entries.
- `xet-core` uses adaptive concurrency for xorb uploads (start conservative, scale with bandwidth, back off under congestion).

### Integrity & idempotency

- Same chunk data ⇒ same chunk hash; same chunk set ⇒ same xorb hash; consistent chunking ⇒ identical data splits at identical boundaries (enabling dedup).
- Upload endpoints are idempotent w.r.t. content-addressed keys; re-sending an existing xorb or shard is safe (`was_inserted: false` / `result: 0`).

## 7. C# implementation checklist (derived)

- Disable auto-redirect on the resolve request to read `X-Xet-Hash`.
- Implement the 8-byte-region little-endian hash-to-hex conversion as a shared utility; use it everywhere a hash becomes a string.
- Token manager per (repo, ref, scope): cache until `exp - 30s`, refresh via same Hub endpoint; on CAS `401`, refresh and retry once.
- Reconstruction client: prefer `/v2/reconstructions`, fall back to `/v1` on 404/501; send `Accept-Encoding: gzip` (or `zstd` if available); honor `Range` semantics (request inclusive-end; `offset_into_first_range` skip; output truncation).
- Multi-range GETs: `Range` header must exactly match the signed set; parse `multipart/byteranges` (System.Net.Http `MultipartReader`/manual boundary parsing — note `HttpClient` doesn't parse it automatically).
- Enforce `unpacked_length` validation per term; fail the download on mismatch.
- Upload ordering: await all referenced xorb uploads before shard POST; split shards > 64 MiB; treat `was_inserted:false` and `result:0` as success.
- NDJSON stream reader for `/v2/shards` with per-line JSON events and terminal-event-based success detection; fall back to `/v1/shards` on 404.
- Retry policy: exponential backoff on 429/500/503/504 and connection errors; never retry 400/403/404/416; 401 ⇒ token refresh path.

## 8. What live traffic adds

Captured 2026-08-16 against `huggingface.co` and `cas-server.xethub.hf.co`, downloading
`xet-team/xet-spec-reference-files` and `openai-community/gpt2` while building the download
pipeline. Sanitized copies of the responses are vendored in
`tests/XetSharp.Tests/CapturedResponses/`. Everything below is observed behaviour, not spec text —
it can change without the spec changing.

### 8.1 Anonymous access works

No `Authorization` header at all, on either the resolve endpoint or `xet-read-token`, returns a
normal Xet read token for a public repository (`user_id=public` shows up in the signed URLs). The
spec lists the header as required, so this is a courtesy, not a guarantee — but it means a client
needs no credentials to download public files.

### 8.2 The resolve response points at auth with `Link`, not `X-Xet-*`

A resolve `302` carries `X-Xet-Hash`, `X-Linked-Size`, `X-Linked-Etag`, `X-Repo-Commit`, and:

```txt
link: <https://huggingface.co/api/datasets/{repo}/xet-read-token/{commit}>; rel="xet-auth",
      <https://cas-server.xethub.hf.co/v1/reconstructions/{file_id}>; rel="xet-reconstruction-info"
```

There are no `X-Xet-Cas-Url` or `X-Xet-Access-Token` headers. The `rel="xet-auth"` URL is the same
token endpoint §1 documents, already pinned to the resolved commit.

Two more things the headers give away for free:

- `X-Linked-Etag` is the file's **SHA-256** (quoted), so a whole-file download can be checked against
  it as well as against its file ID.
- `HEAD` returns exactly the same headers as `GET`. Worth preferring: a file that is *not* on Xet
  answers a redirect-less `GET` with the file itself.

### 8.3 The signed range is inside the CloudFront policy

The spec's examples show the authorized range as an `X-Xet-Signed-Range=bytes%3D0-131071` query
parameter. Current Hub traffic does not include that parameter — the constraint lives inside the
signed `Policy` blob instead:

```json
{"Condition": {"ByteRange": {"ExpectedHeader": "bytes=0-50468"}}}
```

Same rule, less visible: the `Range` header must match that string, and a `GET` with no `Range` at
all is **403**, not a full-object download. A client should still echo `X-Xet-Signed-Range` verbatim
when it *is* present, and otherwise format the ranges itself as `bytes=s1-e1,s2-e2` with no spaces.

*(.NET detail, verified at the socket in `RangeHeaderWireFormatTests`: `TryAddWithoutValidation`
does put the exact string on the wire, but reading the header back through the typed API reformats
it — a multi-range value comes back with `, ` separators. Assert on `Headers.NonValidated`.)*

### 8.4 The stored xorb object is larger than the reconstruction's ranges

For the reference xorb, the CDN object is 14,769,749 bytes while the reconstruction's byte range
covering all 796 chunks ends at 14,737,812 — the object carries a trailing block past the last chunk
record. Download never sees it, because the signed range stops at the chunk data. This is consistent
with the four trailing `XETB` bytes the reference `.xorb` artefact ends with: a xorb reader must stop
at the last complete chunk record rather than assume the data ends on one.

### 8.5 The v1 `fetch_info` entry shape

The spec names `CASReconstructionFetchInfo` without giving its fields. Live `/v1/reconstructions`:

```json
"fetch_info": {
  "<xorb hash>": [
    { "range": { "start": 0, "end": 2 }, "url": "https://…", "url_range": { "start": 0, "end": 50468 } }
  ]
}
```

`range` is the chunk range (end-exclusive) and `url_range` the byte range (end-inclusive) — the same
pair v2 nests under `ranges[].chunks` / `ranges[].bytes`, one per URL instead of many. Both versions
were served for the same file at the time of capture, and parse to identical reconstructions.

### 8.6 Reconstruction responses are gzipped only if asked

`--compressed` (i.e. `Accept-Encoding: gzip`) gets `content-encoding: gzip`; the response is
otherwise plain JSON. For a 796-chunk file the body is under 1 KB, but a multi-gigabyte file's
reconstruction is worth compressing, as the spec advises.
